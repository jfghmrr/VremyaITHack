# Решения, исходные параметры и ограничения

Документ описывает фактическую реализацию. Датированные разделы ниже сохраняют историю изменений; при расхождении с ними актуальные сведения о музыке находятся в разделе «Каталог песен — актуально на 16.10.2026». The rules added by the hackathon upgrade (precise scoring, voice consent, own tracks, sign-in, limits, retention, catalog gates, deployment) are in the last section, «Hackathon upgrade — 16.10.2026»; where an older section disagrees, that section wins. Числовые параметры — **стартовые настройки из ТЗ, а не результат исследований**. Их нужно калибровать по реальным матчам. Все игровые параметры собраны в `GameConfig` (`crates/api/src/config.rs`) и переопределяются JSON-файлом из переменной `GAME_CONFIG`.

## Продукт и бренд

- Название сайта — **Перепев** (Perepev), по прямому указанию владельца. Поиск товарных знаков и свободных доменов в этой работе не проводился.
- Основная навигация: «Главная», «Песни», «Дуэли», «Лидеры», «Мой прогресс». Одиночное пение не требует регистрации. Живые дуэли требуют кабинет; вызов-призрак — нет.
- Выбраны две небольшие функции:
  1. **«Побить свой рекорд»**: лучшая попытка по песне хранится в браузере как каноническая кривая без звука, и её можно выбрать призраком на экране проверки микрофона.
  2. **Повтор фрагмента по кругу** на экране тренировки.

  Обе используют уже существующие механизмы (призрак, тренировку) и не добавляют экранов.

## Оценка (scoring-core)

- Поведение прежнего TypeScript-скоринга — исходная спецификация. Формулы, веса 0.45 / 0.25 / 0.15 / 0.15, пороги, окно задержки ±300 мс, локальная тональность с учётом фраз, октавы и регистра, защита от тишины и постоянной ноты, тексты объяснений перенесены без изменений. Версия алгоритма — `ALGORITHM_VERSION = 1`.
- **Допуск при сравнении реализаций нулевой: результаты совпадают бит в бит.** Обоснование: в оценке нет приближённых функций, только `+ − × ÷`, `sqrt`, `floor`, `ceil` и остаток, точно определённые IEEE-754 и одинаковые в Rust и JS. Порядок операций сохранён. Отличающиеся места JS воспроизведены явно: `Math.round` (половина к +∞), `Math.min/max` с NaN и знаком нуля, устойчивая сортировка, `slice` с отрицательными индексами. Единственное послабление при сравнении: −0 равно +0.
- Эталоны: 93 случая одиночной оценки, 81 случай дуэльной сетки 50 мс, 400 пар исходов и 6 кривых коррекции. Генератор — `tools/fixtures/generate.ts`, он вызывает старую реализацию. В эталонах есть +5 и −7 полутонов, октавы, задержки ±, вибрато, тишина, дрейф тональности, значения у порогов интервалов, ритма, покрытия и постоянной ноты, пропуски, дубликаты и перемешанный порядок кадров, нечисловые значения, одинаковые потери (проверка устойчивой сортировки моментов) и случайные исполнения.
- Ничья определяется так: оба итога округляются до двух знаков, равные значения — ничья. Канонический балл уже округлён до 0.1, поэтому правило совпадает с прежней дуэлью, и все 400 пар дают прежний исход. Неокруглённый балл сохраняется (`rawScore`, `match_participants.raw_score`).
- Одиночная попытка оценивается в браузере (WASM в Web Worker) по кадрам 10 мс. Это личная статистика, а не доверенный результат. Матч сервер всегда пересчитывает сам (native), по канонической кривой 50 мс / 0.1 полутона, одинаковой для обоих участников. Баллы от клиента не принимаются. Since 2026-10-16 a solo attempt can also get a server score (`precise-1`) from the GPU worker's evidence when the singer gave the voice consent; it is still personal statistics, not a trusted competitive result.

## Живые матчи

- Состояния: `created → waiting → ready_check → countdown → singing → collecting → finished`, отдельно `cancelled` (до начала пения, без рейтинга) и `failed` (сбой, без результата и рейтинга). Технический исход отмечается флагом `result.technical`.
- Перед стартом каждый клиент загружает эталон и запись с вокалом, получает микрофон и активирует AudioContext жестом «Я готов». Сервер проверяет версию эталона (SHA-256 файла) и версию алгоритма. Старт назначается через `countdown_seconds = 4` с. Клиент оценивает смещение часов по ping/pong (берётся замер с наименьшим RTT из последних 10) и планирует звук по часам AudioContext.
- Кадры привязаны к времени исполнения относительно старта, а не ко времени прихода пакета. Кривая уходит пакетами примерно каждые 100 мс. Точка отправляется, только когда после неё уже есть кадры дальше окна сопоставления (35 мс + запас): такая точка окончательна и совпадает с полной канонической кривой. После конца песни уходит остаток и `finish`.
- Сервер принимает только первое значение каждой точки, поэтому повтор не меняет кривую. Точки из будущего (больше 1,5 с вперёд по часам сервера) отклоняются. Поздние точки принимаются не позже чем через `disconnect + return_window + 5` с после своего времени. Переподключение не даёт времени перепеть фрагмент, а дозалить уже записанное — даёт.
- Индивидуальной паузы в живом матче нет. Esc предлагает выход и предупреждает о последствиях.
- Восстановление: heartbeat 5 с, разрыв подтверждается после 15 с без сигнала (TTL присутствия), окно возврата — ещё 15 с. Общий таймер при этом идёт.
- Правило технического исхода:
  - выход или невозвращение после начала пения — поражение этого участника, соперник побеждает;
  - неполная кривая к концу сбора (20 с после песни) — поражение того, у кого она неполная;
  - если ни у кого нет полной кривой, или временное состояние матча потеряно после старта, — `failed` без результата;
  - до начала пения отказ или неподтверждение отменяют матч без рейтинга. Подтвердивший участник рейтинговой очереди возвращается в поиск с прежним временем входа.
- Если победитель не увидел финальный экран, итог доступен через `GET /api/matches/{id}` и приходит при следующем подключении (`hello`).
- Сопернику передаются имя, ранг или статус калибровки и линия высоты 50 мс. Серверу — то же плюс служебные события. Звук остаётся в браузере. Кривые матча хранятся в Valkey 2 часа, в PostgreSQL — 30 дней для разбора споров, затем удаляются фоновой задачей (`curve_retention_days`).
- Пересчёт по клиентской кривой **не доказывает, что человек действительно пел**. Это не античит и не платформа для турниров с призами.

## Подбор, рейтинг и ранги

- Elo с калибровкой: старт 1000; первые 10 рейтинговых матчей — калибровка; K = 40 на калибровке, 24 после; E = 1 / (1 + 10^((Rсоп − Rигр)/400)); S = 1 / 0.5 / 0; MMR хранится как `double precision` без округления и округляется только для показа.
- Журнал `rating_events` хранит MMR до и после, K, E, S и MMR соперника. Рейтинг восстанавливается последовательным применением записей, двойное применение исключено ограничением `UNIQUE (match_id, user_id)`.
- Ранги после калибровки: < 1000 «Новичок», 1000–1199 «Любитель», 1200–1399 «Исполнитель», 1400–1599 «Вокалист», ≥ 1600 «Виртуоз». До конца калибровки показывается «Калибровка n/10».
- Очередь одна общая. Фрагмент выбирается после подбора: меньше всего сыгранный обоими за 30 дней, при равенстве — детерминированно по идентификатору матча.
- Окно близости: ±80, каждые 15 с +20, максимум ±150. Критерий должен подходить обоим игрокам. Среди подходящих приоритет у дольше ждущего. Участники калибровки ищутся только в отдельном пуле калибровки.
- Защищаемый новичок: калибровка пройдена, меньше 20 рейтинговых матчей, MMR ниже 1100. Ему не подбирается игрок с текущим или историческим (`peak_mmr`) MMR от 1400, разница не больше 100 при любом ожидании. Пик не уменьшается при поражениях. Правила перепроверяются в транзакции PostgreSQL под блокировкой рейтингов при создании матча.
- Пустая очередь: через 30 секунд честно предлагаются ожидание, друг или призрак. Ботов, выдуманного онлайна и скрытого бесконечного расширения нет.
- Сговор и накрутка: одна пара может сыграть не больше 3 рейтинговых матчей за сутки (`pair_daily_limit`), дальше подбор их не сводит. Честных игроков молча не штрафуем. Дружеские матчи, призраки, одиночные попытки и реванши с другом рейтинг не меняют. Более тонкое выявление сговора (анализ кривых) не реализовано.
- От смурфинга абсолютно не защищаемся: по пустому новому аккаунту нельзя узнать силу певца. Защищены известные новички от известных сильных игроков.

## Надёжность и масштабирование

- Valkey хранит временное состояние: заявки, присутствие, потоки команд и событий матчей, снимки, кривые, аренды. PostgreSQL хранит окончательные данные. Общей транзакции между ними нет, поэтому:
  - пара формируется в три шага (Lua-резерв → транзакция PostgreSQL → Lua-финализация);
  - зависшие резервы восстанавливает лидер подбора;
  - отмена во время резерва отменяет матч до уведомления игроков.
- У матча один владелец: аренда в Valkey (6 с, продление каждые 2 с отдельной задачей) с номером поколения. Записи владельца в Valkey проверяет Lua-скрипт, записи в PostgreSQL — условие `owner_gen`. Устаревший процесс ничего записать не может. Матч без живого владельца подхватывает любой экземпляр: каждые 2 с проверяются активные матчи.
- В PostgreSQL состояние матча фиксируется при создании, старте (`countdown`) и итоге. Промежуточные шаги живут в Valkey: каждый коммит ждёт сброса WAL, а на локальном PostgreSQL под macOS это главный расход базы.
- Команды до владельца доходят через поток `m:{id}:in`, события до игроков — через `m:{id}:out`, независимо от экземпляра. Каждый экземпляр держит одно блокирующее соединение XREAD для всех локальных подписок.
- Пересчёт результата идёт в ограниченном пуле (по умолчанию ядра − 1) с ограниченной очередью (64). При переполнении матч остаётся в сборе и пересчитывается на следующем такте.
- Ограничения: сообщение WebSocket до 16 КиБ, пакет до 100 точек, 40 команд/с (всплеск 80), исходящая очередь соединения 512 сообщений (переполнение закрывает соединение, клиент переподключается и получает состояние), потоки матча до 4000 записей, тело HTTP до 16 КиБ (JSON; the upload routes added on 2026-10-16 have their own limits, see the last section).

## Аккаунты и приватность

- Почта и пароль (12–128 символов), серверная сессия на 7 дней в HttpOnly-cookie с `SameSite=Strict` (`Secure` на HTTPS). Изменяющие запросы требуют свой Origin и заголовок `X-Perepev-Request: 1`. WebSocket проверяет Origin, сессию при подключении и затем каждые 30 с. Выход и смена пароля закрывают активные соединения на всех экземплярах.
- Хеши: scrypt N=2^17, r=8, p=1, 64 байта — те же, что в прежней версии, с той же солью (hex-строка как UTF-8). Старые хеши проверяются без преобразования. Одновременно вычисляется не больше двух хешей (по 128 МиБ памяти).
- Cookie сохранила прежнее имя `perepev_session`, чтобы перенесённые сессии продолжили работать после переключения.
- Since 2026-10-16 accounts can also be created through Yandex ID or VK ID: such an account has no email and no password, gets the nickname `Певец-NNNN`, cannot set a password, and confirms deletion with the word «УДАЛИТЬ».
- Удаление кабинета реализовано: после подтверждения паролем (без пароля — словом «УДАЛИТЬ») сразу удаляются аккаунт, сессии, история, рейтинг и участие в матчах; соединения закрываются на всех экземплярах. Во время активной дуэли удаление откладывается до её конца.
- **Подтверждение почты и восстановление пароля не реализованы.** Интерфейс прямо говорит об этом.
- Гостевые попытки хранятся только в браузере и в кабинет не переносятся: у них нет доказательства владельца.

## Законодательство РФ (152-ФЗ)

- Владелец сайта — оператор персональных данных. Документы описывают фактическую обработку: `/legal/privacy` (политика, ст. 18.1), `/legal/consent` (согласие отдельным документом, ч. 1 ст. 9 в редакции 156-ФЗ, с 01.09.2025), `/legal/cookies`, `/legal/music`.
- При регистрации — отдельный флажок согласия со ссылками. Сервер хранит время и редакцию согласия (`users.consent_at`, `consent_version`; the current version is `2026-10-17`, earlier `2026-10-14`). У перенесённых из прежней версии пользователей эти поля пустые: там согласие давалось флажком без записи времени.
- Права субъекта: выгрузка всех данных кабинета в JSON (включая сохранённые кривые дуэлей), смена имени, удаление кабинета (отзыв согласия) с немедленным удалением.
- Cookie только необходимые (`perepev_session`; since 2026-10-16 also `perepev_oauth` for 10 minutes during a Yandex/VK sign-in and `perepev_guest` for 24 hours, set when a guest starts a precise-scoring performance), остальное — `localStorage` на устройстве. Внешней аналитики, рекламы, сторонних шрифтов и счётчиков нет, поэтому плашка информирует и запоминает согласие, а выбор категорий не нужен.
- Реквизиты оператора, уведомление Роскомнадзора, размещение серверов в России (локализация, ч. 5 ст. 18) и график удаления резервных копий — обязанности владельца. В демоверсии документы называют команду mugsize; неизвестные реквизиты не публикуются. Перед публичным размещением сведения о владельце необходимо добавить отдельно. Тексты не проходили юридическую экспертизу.
- Возрастная классификация нового вокального каталога не проводилась. Отсутствие мата не означает автоматически «0+»: в отдельных песнях есть темы утраты и философские образы. Прежнее обоснование маркировки народными мелодиями к новым записям неприменимо. Update 2026-10-16: the site shows a 6+ label in the footer and an age label on every song card. The 8 public-domain songs have an explicit `age` (3 × 0+, 5 × 6+) chosen when their lyrics were screened; the 24 older songs have no `age` field and the card shows the default 0+, which is a UI default, not a separate classification.

## Каталог песен — актуально на 16.10.2026

- 32 подготовленных фрагмента с настоящим вокалом: 14 русских и 18 английских (until the hackathon upgrade: 24 = 10 RU / 14 EN). 24 из них — Josh Woodward, Complex Numbers и проект Виктора Аргонова. The other 8 (added 2026-10-16) are well-known folk and old songs whose music and words are in the public domain in Russia, in free recordings; their gates are listed in the «Hackathon upgrade — 16.10.2026» section. Это небольшая проверенная подборка, не исследование всего интернета и не разнообразие всех жанров.
- Все 25 прежних инструментальных песен исключены из рабочего индекса: новые игры должны использовать только вокальные записи. Архивные файлы оставлены для регрессионных проверок и старых данных; они не считаются доступными песнями каталога. Старые ссылки на исключённые песни могут быть недоступны.
- Записи охраняются авторским правом и включены по CC BY 4.0, CC BY 3.0 US либо CC BY-SA 4.0. Указания одного имени было бы недостаточно: сохранены источники, точные лицензии, участники записи и изменения. Музыкальные адаптации под BY-SA сохраняют BY-SA; MIT кода их не заменяет. The recordings of the 8 public-domain songs are a US federal work, CC0 1.0, CC BY 3.0 or CC BY-SA 3.0; their adaptations keep the recording's licence (CC0 1.0 for the US federal and CC0 recordings).
- Игровые записи — законченные фрагменты до 60 секунд, а не полные песни. Слышен голос исходного исполнителя, на экране есть слова. Наушники нужны, чтобы этот голос не попал в микрофон и не повлиял на результат. Название поля `backing` сохранено, хотя теперь файл содержит вокальный микс. Since 2026-10-16 every song also has machine-separated `instrumental.mp3` and `guide.mp3`; while singing, «В наушниках» plays the instrumental with the guide at low gain and «Без наушников» only the instrumental, and `backing.mp3` is the preview and the fallback.
- Офлайн-подготовка использует официальные вокальные дорожки либо локальный Demucs, локальную разметку Whisper и выделение мелодии pYIN. Текст сверяется с источником/записью, но границы слов и эталон высоты остаются приближёнными. Распевы, бэк-вокал и дыхание способны ухудшать точность. Во время игры ML-модели не скачиваются. The user's audio stays in the browser unless the user gives the voice consent for precise scoring (since 2026-10-16); then it goes to the site's server and the team's GPU PC and is deleted after scoring, at most 10 minutes later.
- Формат `reference.json`, алгоритм оценки и старые эталоны не менялись (the browser and duel algorithm is still version 1; `precise-1` is a separate server algorithm added on 2026-10-16). Совпадение синтетической кривой с эталоном проверяет механику скоринга; оно не доказывает, что автоматически извлечённый эталон безошибочно описывает студийную запись.
- Тексты включённых фрагментов отобраны без мата, явных оскорблений групп людей, призывов к насилию и наркотической тематики. Названия и авторы сверены с официальной выгрузкой федерального списка экстремистских материалов 16.10.2026. Это ограниченная редакторская проверка, не заключение о соблюдении всего законодательства РФ. Дата, метод и хеш выгрузки — в `docs/vocal-catalog.md`.

## Аудио

- Детектор высоты — pitchy (MIT), параметры прежние: окно 2048, clarity ≥ 0.85, RMS ≥ 0.008, 65–1100 Гц, медиана трёх кадров. Он работает в Web Worker: AudioWorklet передаёт ему окна напрямую через MessagePort, основной поток получает только кадры.

## Hackathon upgrade — 16.10.2026

Rules and decisions in force after the upgrade for the 2026-10-17 defense. Sources: the design `docs/superpowers/specs/2026-10-16-hackathon-upgrade-design.md` (its §6a overrides the rest), the plan `docs/superpowers/plans/2026-10-16-hackathon-upgrade.md` (contracts C1-C4) and the rulings the builder made on the owner's behalf during the work. Numbers are starting values, not research results, unless a measurement is named.

### Precise scoring

- **Tag and scope.** The server algorithm is `precise-1` (`crates/scoring-core/src/precise.rs`). It scores solo attempts only. Duels and rated matches keep `ALGORITHM_VERSION = 1` and their server-side curve scoring.
- **Weights** stay 0.45 intervals / 0.25 rhythm / 0.15 stability / 0.15 coverage. When words are checked, the second axis becomes «Ритм и слова» = 0.5 × rhythm + 0.5 × words score.
- **Words.** Per lyric word: `sung × timing`. `sung` (0..1) comes from the worker; `timing` is 1 when the onset, after removing the found lag, is within 0.20 s of the reference, falling linearly to 0 at 0.60 s. A word without evidence counts as 0. A word counts as sung at `sung ≥ 0.5`.
- **Caps.** Low coverage and a constant tone → 30 (unchanged). Guide-vocal bleed ≥ 0.45 → 30 (`bleed`). Words checked and fewer than 30% sung → 40 (`words`). The strictest cap that fired is reported, on a tie the later one; `cap` is shown even when the raw score was already lower.
- **Lag.** The ±0.3 s latency window stays (spec). Takes later than that, typically Bluetooth output, score very badly; wired headphones are the advice for the defense.
- **Words check per song** (ruling 2026-10-17). A catalog song can carry `"wordsCheck": false` in `index.json` (default true). Its score jobs are sent without lyric words, so the final score is melody and rhythm only, marked «слова не проверены», with no words cap; the bleed and coverage caps still apply. Set for «Ямщик, не гони лошадей», «Ой, то не вечер» and «Дорогой длинною» because Whisper recognised no words even in their own vocal on production (a clean take got the cap of 40). Own tracks always check words.
- **Word evidence on the worker.** openai-whisper (`large-v3-turbo` on CUDA, `small` on CPU) without a lyrics prompt, so it cannot echo the lyrics, then a monotonic fuzzy alignment with the known lyric words (rapidfuzz ratio ≥ 70; `sung` = ratio / 100; onset from the recognised word). A masked lyric word is compared with the masked recognised word. Ruling: openai-whisper instead of faster-whisper, because CTranslate2 needs extra CUDA DLLs on Windows, an install risk before the defense.
- **Bleed method.** GCC-PHAT between the recording and the played stems (200-4000 Hz, lags ±0.5 s), turned into 0..1; the instrumental's contribution is projected out before the guide is measured. Ruling: accepted instead of the plan's 50 ms RMS-envelope correlation, which measured 1.01 for a singer singing along (it would cap every real singer) and 0.17 for real phone bleed (it would miss it).
- **Bench ruling.** The benchmark's "perfect" take is a sample copy of the guide stem, which is exactly what the bleed check must catch, so it gets the bleed cap by design; the ±3-semitone takes (87.1-98.9, no cap) are the valid perfect-singer stand-ins. No threshold was changed. A real person singing along in headphones mode was not measured.
- **Models.** Pitch: torchcrepe `full` for references and recordings (RMVPE not used). Separation: Demucs `htdemucs` (Mel-Band RoFormer not used). Browser live pitch stays `pitchy` (SwiftF0 deferred). Qwen3-ASR / ForcedAligner deferred. Apple MPS is never used; on the Mac the worker runs on CPU only.
- **Deadlines.** Worker liveness: last lease or heartbeat younger than 30 s. Score deadline: 20 s after finish (`PERF_DEADLINE_S`). The client gives up after 25 s. Lease long poll 25 s, lease TTL 120 s renewed by heartbeat and progress.
- **Fallback.** Worker offline, refused upload, failed job or no answer in time → the browser score becomes final with «слова не проверены». Only the server's score and axes replace the browser's; the pitch line, moments and lag stay from the browser analysis.
- **History.** Attempts store `algorithm = "precise-1"` and `words_checked` for a server score; browser scores store NULL / false; older rows stay NULL.

### Voice recording and consent

- A one-tap consent before the microphone, for guests and signed-in users alike, stored as the consent version `2026-10-17` in `perepev.voiceConsent` and asked again when the version changes. Ruling: declining is allowed and keeps the browser score; the terms promise that.
- Upload only with consent: 16 kHz mono PCM16 in 5 s chunks, from the countdown, ≤ 400 KB per chunk and ≤ 70 s in total; the sound mode and consent version are sent with it.
- Ruling (data minimisation): `POST /api/perf` answers 503 when no worker is configured or its heartbeat is older than 30 s, so no voice is accepted that cannot be scored. The refused attempt still uses one rate-limit slot.
- The voice is deleted after scoring and at most 10 minutes after the performance was created (sweep at 7 min, checked by a compile-time bound). Performance records and precise results are kept 24 hours.
- The voice is used only for scoring: no identification and no voiceprints. The legal research of 2026-10-16 treats it as ordinary personal data, not biometrics (spec §9; not legal advice).
- Guests: the `perepev_guest` cookie (random, HttpOnly, SameSite=Strict, 24 h) only ties an upload to its result in that browser. Limits are per IP; the spec's per-browser guest limit was not built.

### Own tracks

- Sign-in required; 5 uploads per user per 24 hours.
- In the browser: file ≤ 30 MB, duration 15 s to 10 min, checked from the header, by a metadata probe and again after decoding (ruling: keep the 10-minute cap; decoding a long file peaks at about 320 MB, acceptable on current phones). Only the chosen 15-60 s section plus 2 s margins is uploaded, as 44.1 kHz mono 16-bit WAV (server limits: 12 MB, 14-70 s).
- The track is private (owner-only routes) and deleted with its files after 24 hours. A track job not finished 30 minutes after it was created fails. Recognised obscene words are masked on screen.
- Ruling: track job params carry `track_id`, and the worker names the song `my-<track_id>`, because the client rejects a reference whose id differs from the requested song id. Catalog ids may therefore never start with `my-`.
- A failed audio upload is retried on the same track, so it does not use another daily upload.
- Known gap: «Поделиться» on an own track builds a challenge link that a friend cannot open.

### Sign-in, accounts and legal texts

- Yandex ID and VK ID (authorization code with PKCE S256) plus the existing email and password; no Google (149-FZ Art. 8 part 10, per the spec's research). - Every sign-up asks for the age group (`14plus` / `under14`); under 14 requires a parent's or guardian's name (2-64 characters), stored with the consent. Ruling: the consent version is `2026-10-17` on the server and in the client.
- The contacts form is a general request form (data questions, consent withdrawal, rights-holder complaints). Ruling: the link field is optional. Ruling: requests are deleted after one year, and the privacy policy says so.
- The operator is the stub «Команда mugsize»; no invented INN, OGRN, address or Roskomnadzor number. The privacy policy states storage in Russia, which holds for the Russian server, not automatically for any local install.
- Site label 6+ in the footer; age label on every song card.

### Catalog additions

### GPU worker and installer

- The worker only makes outbound HTTPS requests; the server stores only the SHA-256 of its token.
- Ruling: on Windows the token is encrypted with DPAPI machine scope (the task runs as SYSTEM and cannot read a user-scoped blob), and `C:\Perepev` is restricted to SYSTEM and Administrators. Any local administrator can read the token; they could anyway.
- The installer does not install Python or ffmpeg through winget: uv brings a managed Python 3.12, and audio goes through libsndfile. The self-test uses a synthetic clip, not a bundled one.
- Ruling: the builder installed the worker on the owner's PC over SSH, at the owner's request, to test the CUDA path before the defense; `setup.ps1 -Uninstall` removes it.

### Deployment

- Ruling: the public site runs behind the server's existing host nginx (it already holds ports 80 and 443 for other sites); the containers listen on `127.0.0.1:8097`, and nginx terminates TLS with a certbot certificate. External port 80 of that server reaches another device, so the installer defaults to DNS-01 through the server's existing Cloudflare key.
- Ruling: the nginx and certificate step is a script the owner runs once with sudo; no workaround for root.
- Caddy trusts `X-Forwarded-For` only from private addresses in the local and nginx modes and from nobody in `compose.server.yaml` mode.
- Access log (fixed 2026-10-17): the site template turns the host nginx's access log off for the HTTPS server as well as the port-80 one, so normal requests leave no client address on the host, in line with the one-hour IP rule of the privacy page and the data export. It takes effect once the owner re-runs `sudo bash deploy/nginx/install-site.sh`; until then the installed site file still logs HTTPS requests. Ruling: the error log stays; it records the client address only for failed requests (for example an unreachable upstream), with the server's own retention.
- Caching (2026-10-17): Caddy sends `Cache-Control: no-cache` on pages and `/_app/version.json`, so a redeploy cannot leave browsers on a stale page whose hashed chunks are gone; `/art/*` is cached for 7 days and a missing image is a 404. Song files stay `no-cache` until their URLs carry a content hash.
- Ruling: the owner's old local install (Compose project `kvinta`) stays as it is, at the owner's instruction; its database was backed up first.
